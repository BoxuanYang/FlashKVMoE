Qwen3-30B-A3B：单卡 GPU + KT CPU MoE + FlashInfer

将修改后的代码同步到服务器，在仓库根目录执行以下命令。
沿用 docs/ktransformers.md 中的 minisgl-kt 环境（CUDA Toolkit 和编译器安装在 Conda 环境内）。

一、准备环境

conda activate minisgl-kt
export CUDA_HOME="$CONDA_PREFIX"
export PATH="$CUDA_HOME/bin:$PATH"
export CC="$CONDA_PREFIX/bin/x86_64-conda-linux-gnu-cc"
export CXX="$CONDA_PREFIX/bin/x86_64-conda-linux-gnu-c++"
export CUDAHOSTCXX="$CXX"
python -m pip install -e .

首次启动会编译并缓存 Marlin CUDA 内核，需要 nvcc、C++ 编译器和 ninja。
保留 third_party/ktransformers 子模块的完整源码，无需安装 archive 的旧 Python 运行时。

可先单独编译，成功后再启动服务（与服务使用相同环境和 GPU）：

CUDA_VISIBLE_DEVICES=2 python -u -c 'from minisgl.layers.marlin import marlin_gemm; marlin_gemm(); print("Marlin ready", flush=True)'

编译会显示 Ninja 输出，但单个 nvcc 编译步骤仍可能长时间没有新输出。
可另开终端执行下面的命令，查看编译进程的 CPU 活动；该阶段不是 GPU 推理：

ps -eo pid,ppid,etime,pcpu,pmem,args | grep -E '[n]inja|[n]vcc|[c]icc|[p]txas'

二、启动（关闭 CUDA graph，沿用原参数）

CUDA_VISIBLE_DEVICES=2 python -m minisgl \
  --host 0.0.0.0 --port 30000 \
  --model /data2/models/Qwen3-30B-A3B \
  --dtype bfloat16 --tp-size 1 \
  --moe-backend kt \
  --kt-weight-path /data2/models/Qwen3-30B-A3B-GGUF \
  --kt-cpuinfer 128 --kt-threadpool-count 2 \
  --kt-method LLAMAFILE \
  --attention-backend fi --cuda-graph-max-bs 1 \
  --page-size 1 --num-pages 2048 \
  --max-seq-len-override 2048 \
  --max-prefill-length 2048 --max-running-requests 100

所有权重只从 --kt-weight-path 的完整 GGUF 加载；分片 GGUF 请传全部分片所在目录。
--model 目录只需 config/tokenizer，无需 safetensors。
QKV/O 投影和 LM head 自动使用 Marlin INT4，不需要新增启动参数。
加载时在 CPU 反量化并重新量化为 Marlin 格式，再传到 GPU，会引入额外量化误差。
Embedding、norm、router、激活和 KV cache 仍为 BF16，因此保留 --dtype bfloat16。

curl --fail-with-body http://127.0.0.1:30000/v1/chat/completions \

四、Qwen3-30B-A3B：同时发送 4 个请求，每个输入 4096 tokens

先停止原服务，使用下面的参数重新启动。原来的 2048 上下文上限无法处理 4k 输入。
这里每个请求再生成 256 tokens，因此序列上限至少为 4352；4 个请求共需容纳约
17408 tokens 的 KV cache，下面预留 18432 页（page-size=1）。
max-prefill-length=16384 允许一批处理最多 4×4096 个输入 tokens；是否实际合批由调度决定。

CUDA_VISIBLE_DEVICES=2 python -m minisgl \
  --host 0.0.0.0 --port 30000 \
  --model /data2/models/Qwen3-30B-A3B \
  --dtype bfloat16 --tp-size 1 \
  --moe-backend kt \
  --kt-weight-path /data2/models/Qwen3-30B-A3B-GGUF \
  --kt-cpuinfer 128 --kt-threadpool-count 2 \
  --kt-method LLAMAFILE \
  --attention-backend fi --cuda-graph-max-bs 0 \
  --page-size 1 --num-pages 18432 \
  --max-seq-len-override 4352 \
  --max-prefill-length 16384 --max-running-requests 4

等待服务就绪，另开终端，在同一环境、仓库根目录运行：

python send.py

脚本使用本地同一份 tokenizer，校验每个完整输入（含聊天模板）恰好为 4096 tokens。
四个上下文分别来自 LongBench 的 narrativeqa（小说）、qasper（论文）、gov_report
（政府报告）、qmsum（会议记录），各取一篇足够长的原文并截断，不重复填充正文。
首次自动下载官方 data.zip（约 114 MB），之后使用 Hugging Face 本地缓存；下载和分词
不计入请求耗时。数据来源：https://huggingface.co/datasets/zai-org/LongBench
脚本打印每篇上下文的来源 ID，以及四个完整输入两两之间的最长公共 token 前缀。
每轮使用新的随机前缀，避免重复运行命中上轮正文缓存；聊天模板仍可能共享少量前缀。
每个请求设置 ignore_eos=True，目标输出 256 tokens。输出首段文本延迟、总耗时、
回复预览和整轮吞吐。耗时包含排队，输出 token
数由返回文本重新分词估算，因为当前服务的 usage 返回 0。
同时提交 4 个请求不保证它们属于同一 prefill batch，以服务端调度日志为准。

如果服务地址或模型目录不同：
python send.py --url http://127.0.0.1:30000 --model /data2/models/Qwen3-30B-A3B

如果修改 --output-tokens，需要相应增加服务端的序列上限与 KV cache 容量。
